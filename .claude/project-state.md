**A real correctness bug found and fixed during verification, not just cosmetic tuning:** Treatment Journey's `pin` silently failed to stick (`position:sticky` computed but rendered at the wrong offset, not stuck to viewport top) because `Section`'s non-`bleed` mode wraps children in an auto-height `Container` *outside* `data-sc-stage` — that extra ancestor's height collapses to match the stage's own height, leaving `position:sticky` no room to stick across the pin's scroll range. Brand Statement's working pattern (`Container` *inside* the stage) was the fix, applied to Journey too. Caught by directly measuring `getBoundingClientRect()` mid-verification, not by eye — the visual symptom (content just scrolling normally instead of holding) is easy to mistake for "not scrolled far enough yet."

**A second real bug, mobile-specific, also found and fixed:** both `pin` acts with multi-item stacked content (Brand Statement's 3 beats, Treatment Journey's 5 steps) can be genuinely taller than one small-phone viewport once Tailwind's responsive grid collapses to a single mobile column — and a pinned stage's `overflow:clip` then permanently hides whatever's below the fold, since the stage never scrolls internally (confirmed by measurement: Journey's 5th step sat ~200px below the visible 844px-tall stage on a 390px-wide device, unreachable at any scroll position). Fixed generically rather than per-section: `data-sc-mobile-flow` is a new opt-in marker (`src/components/motion/ScrollCraftMount.tsx`) that, on viewports under 768px, rewrites an act's `data-sc-act` from `"pin"` to `"flow"` (and drops `data-sc-span`) *before* `mount()` reads the DOM — mobile gets a genuinely different, unpinned sequential reveal instead of a pin sized for a screen it doesn't fit, satisfying the phase's "adapt, don't scale down" requirement for these two sections specifically (Before/After peak's pin was measured and confirmed to fit one mobile viewport exactly as-is, so it was left pinned). Known limitation: this only resolves at mount time, not on a live resize crossing the 768px breakpoint mid-session (rotating a tablet, resizing a desktop window) — acceptable for this phase, noted below.

**Shared-component fixes required to make any of this possible:** `Section.tsx` and `Container.tsx` had strict prop types with no passthrough — extended both to spread `...rest` (`Omit<ComponentProps<"section"|"div">, ...>`) so `data-sc-*` attributes can reach the underlying DOM element at all; every section using these primitives needed this. `SectionHeading.tsx`'s `as?: ElementType` narrowed to `as?: "h1"|"h2"|"h3"|"h4"` — a fully generic `ElementType` collided with `@react-three/fiber`'s global `JSX.IntrinsicElements` augmentation (its huge tag union collapsed the inferred `children` prop type to `never`, a real `tsc` error, not a style nit); `as` was never actually used with a non-default value anywhere in the codebase, so this cost nothing. `ImageWrapper.tsx`'s figure gained a default `overflow-hidden` (needed for Explorer's new hover-scale to clip correctly; audited safe for every other caller).

1. Long, adjective-stacked "editorial photography, cyclorama, medium-format..." prompts caused the 4-step distilled model to default to generic abstract white blobs instead of the described subject. 2. Doctor portraits with explicit "Saudi woman/man" + long attire descriptions rendered wrong ethnicity/gender at 4 steps (weak demographic fidelity is a real limitation of this specific fast/small model, not a prompt bug). Shortened to "Middle Eastern woman/man, [age], [one feature], wearing [blazer]" — much better, still not guaranteed-accurate, acceptable given the fictional-brand disclaimer already on the page.

## Important decisions

- No backend/DB/auth/CMS — frontend-only per Tech Stack §18, enforced in CLAUDE.md anti-overengineering rules.
- Skill usage is a hard gate: understanding a skill's philosophy ≠ invoking it. Mandatory skills (`scroll-craft`, `frontend-design`, `gsap-skills`, `arabic-design`, `cro`, `impeccable`) and QA skills (`performance`, `core-web-vitals`, `accessibility`, `chrome-devtools-mcp`, `web-quality-audit`) must be invoked in their required phase; if one can't load, stop the phase rather than approximate.

- **Color:** bone canvas (`#F6F2ED`) / warm-black ink (`#201B18`) / deep-wine accent (`#5C2333`) — chosen specifically to avoid both the medical-blue default and the cream+brass "artisan" cliché the scrollcraft skill flags as an overused non-choice.
- **Typography:** Fraunces (display) + General Sans (body/UI); Noto Kufi Arabic + IBM Plex Sans Arabic as the Arabic direction — General Sans self-hosted (Fontshare, not on Google Fonts), the other three via `next/font/google`.
- **RTL implementation:** direction-aware type tokens (font family, tracking, leading) flip via a `[dir="rtl"]` CSS-variable override rather than per-component logic — one cascade point, applied per the `arabic-design` skill's hard rules (no negative/positive tracking on Arabic, ≥1.3 line-height on Arabic display).
- **Tailwind v4**, CSS-first `@theme` tokens in `globals.css` — no `tailwind.config.js`, matches current create-next-app default and keeps all tokens in one file.
- **Bilingual content model:** mock data uses one dataset with `LocalizedText = {en, ar}` fields, not separate English/Arabic data files.
- **Next.js 16 rename:** middleware lives at `src/proxy.ts`, not `middleware.ts` (framework convention change; avoids a build deprecation warning) — same next-intl middleware function either way.
- **Motion grammar:** Filmic one-shot, not literal scrollcraft "Continuous world" — the user asked to attempt one continuous world, but Continuous World's hard bans (no section boundaries, no acts, waypoint-map-only nav) are incompatible with LUMÉ's non-negotiable persistent-CTA nav, interactive Treatment Explorer, booking form, and accessible footer. Filmic one-shot delivers the unbroken-world feeling via `drift` instead. Full reasoning in LUME_CREATIVE_DIRECTION.md.
- **Signature move:** the Before/After section becomes a scroll-scrubbed transformation reveal (`--sc-p`-bound `clip-path`, both scroll directions) — this is the page's engineered peak, not a mouse-drag slider.
- **3D:** exactly one moment (Brand Statement "Science" beat, lazy-loaded R3F), not a WebGL showcase.
- **Placeholder-image system:** `SpecimenPlate` (grain-textured bone/ink/wine-wash plate + museum-label corner index) stands in for all photography this phase, chosen live over blocking the phase — no image-gen API key was available in this environment. Every consumer passes plain props (`tone`/`index`/`caption`/`aspect`); swapping in real images later is a per-component edit, not a redesign.
- **RHF↔Zod without `@hookform/resolvers`:** `src/lib/formResolver.ts` is a ~15-line hand-rolled resolver using `schema.safeParse`. That package isn't in the Tech Stack §2 dependency ladder and wasn't worth adding for one call site (the booking form).
- **`--color-neutral` darkened** from `#a79c91` to `#6b5f53` (impeccable critique, Phase 04) — the original failed WCAG AA (2.41:1) as sitewide caption/label text. Same warm-taupe family, now ~5.5:1.
- **ScrollCraft engine is the primary motion system (Phase 05), GSAP stays registered but unused.** An initial plan (based on reading only the skill's `SKILL.md`) concluded the opposite — that the engine's literal runtime was React-incompatible and should be reimplemented in GSAP. The user corrected this explicitly and required the decision be based on the actual engine source; reading `scrollcraft.js` in full showed it's markup-driven (`data-sc-*` attributes, one `mount()` call, zero DOM generation) with no React incompatibility at all, and its device vocabulary already covers everything the creative-direction feeling-curve table asks for. Record this so a future phase doesn't re-litigate it from the skill's prose alone the same way.
- **3D distortion tuning:** `IcosahedronGeometry` detail must be ≥5 once per-vertex noise displacement is added — detail 4 reads as the explicitly-banned low-poly-diorama look, not "soft organic liquid," once displaced.
- **`Section`/`Container` now spread `...rest` onto their DOM element** (Phase 05) — needed for any `data-sc-*`/other passthrough attribute to reach the real element at all; every future section using these primitives inherits this for free.
- **Sticky-pin structural rule:** `data-sc-stage` must be the *direct* child of the `[data-sc-act="pin"]` element (or of a plain non-height-constrained wrapper) — never nested inside `Section`'s auto-inserted `Container` (which sits *outside* the stage in non-`bleed` mode). That extra ancestor's auto-height collapses to match the stage's own height, leaving `position:sticky` no room to stick. If `Container`'s padding/max-width is wanted around a pinned stage's content, put `Container` *inside* the stage (see `BrandStatement.tsx`/`TreatmentJourney.tsx`), and pass `bleed` to `Section` so it doesn't also wrap from outside.
- **Embedding a Latin brand name/token inside Arabic prose (Phase 06):** wrap it in Unicode directional-isolate marks (U+2066 LRI … U+2069 PDI) directly in the data string, not an HTML `.ltr` span — this is the only fix that also works in plain-text contexts like the WhatsApp `wa.me` message bodies, which can't carry markup. Applied to every `ar:` string containing "LUMÉ"/"LED" in `config/site.ts`, `data/{treatments,doctors,packages}.ts`, and `lib/whatsapp.ts`. A future clinic swap that puts a new Latin brand name into Arabic copy should follow the same pattern.
- **Per-value translation lookup tables live next to the data, not inline** (`concernLabels` pattern, extended in Phase 06 with `categoryLabels`/`languageLabels` in `src/data/concerns.ts`): any plain-English enum value rendered directly in a component (a category slug, a language name) needs one of these before it can be trusted on `/ar` — check for this class of bug before adding new enum-like fields to `src/data/types.ts`.
- **`scrollcraft.css` is imported into its own `@layer scrollcraft`, pre-declared before Tailwind's layers (Phase 07):** `globals.css` opens with `@layer scrollcraft;` then `@import "tailwindcss";` then `@import "../lib/scrollcraft/scrollcraft.css" layer(scrollcraft);` — this positions the engine's own unlayered color/typography resets below all of Tailwind's layers (theme/base/components/utilities), so `.text-canvas` etc. utilities always win over the engine's `a`/`button{color:inherit}` resets. This was a real, sitewide, P0 CTA-contrast bug before the fix (unlayered CSS always beats layered CSS regardless of specificity — the engine's own resets were unlayered plain CSS, imported via a JS `import` in `layout.tsx` at the time). The JS import of `scrollcraft.css` in `layout.tsx` was removed; it's pulled in only via this `globals.css` `@import` now. Never move `scrollcraft.css`'s import back to a plain unlayered JS/CSS import — it will silently reintroduce the bug.
- **`backdrop-filter` establishes a CSS containing block for `position:fixed` descendants (Phase 09, confirmed via `offsetParent`):** same family of rule as `transform`/`filter`/`will-change`, but easy to forget since `backdrop-filter` reads as "just a blur." Navbar's `<header>` has `backdrop-blur-sm`, which silently repositioned the mobile-nav scrim/panel relative to the header's own short box instead of the viewport. The fix is always to portal the fixed-position overlay out from under the blurred ancestor (`createPortal` to `document.body`), not to chase z-index/positioning values on the overlay itself. Check this first for any future `position:fixed` element that renders in the wrong place while computing the right numbers.
- **Site-wide "3D language" was built from ScrollCraft's own pointer/depth primitives (`data-sc-tilt`, `data-sc-parallax`) plus CSS, not new WebGL scenes (Phase 09).** A reusable `tilt` prop on `ImageWrapper.tsx` is the shared mechanism for card-image depth (Explorer/Featured/Doctors/Packages). **Superseded (Phase 10):** the R3F "serum droplet" scene this note originally described as staying was itself removed in the prior-session WIP committed at the start of Phase 10 (`715e095`) — the project now has **no WebGL/3D scene at all**, `three`/`@react-three/fiber`/`@types/three` are no longer dependencies, and Brand Statement's "Science" beat is a plain image. The `data-sc-tilt`/`data-sc-parallax` depth system described above is still exactly as built and still the right mechanism for any future 3D-language work.
- **`--sc-scrim--lead`/`--trail`/`--band` color-mix against `--sc-canvas`, which this project remaps to the cream `--color-canvas` (Phase 09):** using the engine's own scrim classes anywhere on this page paints a *light* gradient, not a dark one — safe only on a build that keeps the engine's default dark canvas. Use an ink-keyed Tailwind gradient (`from-ink/85 ...`) instead for any future contrast-over-image fix.
- **Tailwind v4's `ltr:`/`rtl:` variants did not compile in this project's build (Phase 09, confirmed via direct stylesheet inspection — `translate-x-full` produced zero CSS rules even as a bare untracked class)**: use the `[dir="rtl"]` selector pattern already established in `globals.css` (see the `.sc-copy--lead`/`--trail` overrides, Phase 05) for any future direction-dependent styling instead of reaching for `ltr:`/`rtl:` utilities.
- **Next.js font-preloading is per-layout-file, not per-conditional-branch (Phase 07, confirmed via `node_modules/next/dist/docs`):** splitting `fontVariables` into locale-specific constants inside `src/lib/fonts.ts` and picking one via a ternary in `layout.tsx` does NOT reduce which fonts get preloaded, because `/[locale]` is one shared layout wrapping both locale routes, and Next's font optimization preloads every font function called anywhere reachable from a layout, for all routes that layout wraps — regardless of which runtime branch actually executes. Confirmed by implementing it, rebuilding, and measuring identical byte counts before/after; reverted. A real fix would require separate per-locale route trees, which is a routing-architecture change out of scope for a QA phase — see Known Issues.

## Known issues (final, as of Phase 10)

These are permanent documented limitations, not open items for a future phase — each was investigated and deliberately left as-is:

- **The `pan` device on Featured Treatments has nothing to do at desktop widths ≥~1300px** — all 3 curated cards fit the container without horizontal overflow, so the section renders as a static row there. Only engages at laptop/tablet/mobile widths. Not a bug; noted so a wide-monitor check isn't mistaken for one.
- Treatment Explorer's "All" filter still orphans a single card in the last row at 7 items (unchanged by the Phase 09 concern-group filter change, since the underlying item count is the same) — same longstanding cosmetic issue considered and deferred in Phases 04, 06, and 08.

- `prefers-reduced-motion` has never been exercised via a live browser toggle in any phase of this project (chrome-devtools MCP's `emulate` tool has no such parameter, and there's no raw CDP-send available to call `Emulation.setEmulatedMedia` directly) — the engine's reduced-motion CSS branch was read and is present/correct by inspection in every phase that checked it, but would need an OS-level/DevTools-panel check or the scrollcraft skill's own `shoot.mjs --reduced-motion` to verify live.
- Font loading (`src/lib/fonts.ts`) unconditionally loads all 4 font families on every page regardless of locale — confirmed (Phase 07) to be a genuine Next.js per-shared-layout font-preloading constraint of the `/[locale]` route architecture, not fixable without a routing-architecture change.
- `siteConfig.logo.src` (`/logo.svg`) doesn't exist as a file — harmless, since Navbar/Footer render the brand name as a text wordmark (`siteConfig.logo.wordmark`), not an `<img>`. A template adopter who wants an actual logo mark should add the file and wire it in; not needed for this build.
- Doctor portrait ethnicity/gender fidelity to the written bios isn't guaranteed — a known limitation of the fast 4-step image-generation model used, acceptable given the fictional-brand disclaimer.
- Treatment Explorer's "All" filter grid orphans a single card in the last row at 7 items — cosmetic, needs JS-computed column-spanning to fix properly (the item count changes dynamically with the active filter); considered three times across Phases 04, 06, and 08 and not worth the complexity each time.
- Before/After gallery drag was verified via a programmatic `input` event dispatch, not an actual pointer/touch drag gesture on a real or emulated device.
- `data-sc-mobile-flow` (Brand Statement, Treatment Journey) only resolves the pin→flow rewrite once, at `mount()` time — a live resize crossing the 768px breakpoint mid-session won't retroactively re-type an already-mounted act. The engine doesn't support rebuilding its act list on resize.
- The scrollcraft skill's own `shoot.mjs` verification harness (contact-sheet screenshots incl. `--reduced-motion`) was never run across any phase — all verification was done live via chrome-devtools MCP instead.
- Per-phase skill-invocation verification for Phases 01–06 rests on `project-state.md`'s own contemporaneous prose, not independently-verifiable logs or commit history (repo history was squashed into one commit before Phase 07 — see Phase 08's "Skill-gate verification" note above).
- Unresolved from Phase 02 (see LUME_CREATIVE_DIRECTION.md "Unresolved Decisions"): whether Treatment Explorer deserves a second bespoke interaction beyond concern-filtering — its assigned device per the creative-direction table (`flow`+pointer) is already present via `data-sc-in` + native hover, so this was never blocking; left as a possible future enhancement, not a defect.
